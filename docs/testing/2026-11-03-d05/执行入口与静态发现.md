# 执行入口与静态发现

本阶段真实执行入口是原工作区 `镜像测试/score_compat_20261102.py --stage d05-diagnosis --factor e2e --native-request <本次新请求ID>`，必须由固定原 Harness 总控原生工具启动。`coordinator-source/` 是审核副本，不从文档目录运行；不应通过复制凭据、复用旧批准或另建会话绕过工作区归属。

当前机器状态见 `执行状态.json`。原生批准后任务已实际完成，27个冻结输入×两份已保存真实模型源码，共54次Linux回放，目标模型新调用0。原始等待批准的准备状态已由当前完成记录替代。

结果：每份源码的26个标准/公开/组合/压力输入均通过；扩展元数据探针A通过、B未保留原任务字段，合计A27/27、B26/27。实际资源限制和系统调用过滤均启用，2048任务两份源码分别约3.58/3.79秒。A/B是两份已有模型回复，不能将它们称为本轮新旧代码策略对照。正式当前输入及可信RPC尚未验证，正式分数仍未知。

决策：本范围未复现正式零分；扩展字段是否属于正式契约未确认，不据此修改生产算法。两次自检失败后的选源风险仍需单独故障注入与恢复策略验证。当前提交保持封存2.0.2候选，完整提交次序见发布目录的《当前提交方案-20261103》。

静态发现一：已有两份模型回复在 Windows 的自检记录均为 resource_limits=false/syscall_filter=false，不能据此声称通过Linux隔离。这次会记录容器环境、真实启用的资源限制及过滤状态；未启用的机制不会填为通过。

静态发现二：`LayeredDRunner.prepare_checked_implementation` 两次自检失败后，只要存在完整可解析源码，仍可走 `submit_complete_model_source_for_formal_evaluation`。这条路径没有把真实算法违约与自检环境故障分开；它是待验证的恢复风险，不能单凭静态代码断言是线上唯一根因。任何后续恢复都必须保留当前模型完整源码及来源凭证，不程序修改模型源码、不伪造基线/指标。

静态发现三：一份实际模型源码逐字段重建任务，另一份使用字典复制保留原任务。扩展字段探针用于确认这种差异，但当前不知道正式输入是否有这些字段，不能因扩展探针失败就直接宣称正式缺陷或提高分数。

诊断完成后才选择单一修复因素。标准输入、扩展探针和规模压力分别报告，不混算通过率；若没有复现正式失分就继续保留“线上未定位”的结论，不用测试数量充当得分闭环。
