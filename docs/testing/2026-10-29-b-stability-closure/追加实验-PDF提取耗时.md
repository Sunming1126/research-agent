# 追加实验：PDF 页面提取耗时

日期：2026-10-29

基线候选：0.4.19 / `89912ba4fda95524486088d08cdde88ae7b6f301`
执行方式：用户已授权的离线、无模型实验；不是 DeepSeek Harness 原生执行，也不是平台验收。

## 结论

本轮没有找到值得合入的 PDF 提取提速改动。保留 0.4.19 当前实现：它先用 `get_text("blocks", sort=True)` 提取文本块，再按坐标排序和过滤。两项候选都未达到采纳门槛，因此没有修改生产源码或版本号。

门槛是同一批页面的规范化文本逐页完全一致，并且重复运行显示稳定的墙钟时间和 CPU 时间改善。正确性优先；只要文本不同，就不以速度优势抵消。

## 固定范围与环境

- 冻结语料：60 篇 PDF；每篇最多抽取首 4 页之后的 12 个均匀分布页。部分短文档页数不足，故实际共 612 页。
- 每个实验的不同方法都处理相同的 612 页；每种方法重复 3 次并交替执行顺序。
- 每项实验启动前校验语料 PDF 的 SHA-256。PyMuPDF 版本为 1.24.14，Windows 本地环境。
- 独立网络守卫记录两项实验均为 0 次外连尝试；真实模型调用和 Token 均为 0。
- OS 文件缓存未锁定，因此毫秒级差异不作稳定提速结论。未运行 Linux 容器或官方平台验收。

## 实验 A：改用 `get_text("text")`

| 方法 | 逐页完全一致 | 中位墙钟时间 | 中位 CPU 时间 |
|---|---:|---:|---:|
| 当前 blocks 提取与过滤 | 基准 | 4.889 秒 | 4.766 秒 |
| text 提取 | 608 / 612 页不同 | 11.724 秒 | 11.516 秒 |

候选不仅没有更快，且抽取文本在 608 页不完全一致；墙钟中位数约为当前路径的 2.40 倍。由于页面文本不同，不能把差异解释成“仅格式不同”后直接替换。该候选否决。

## 实验 B：去掉 PyMuPDF 内部排序

候选把 PyMuPDF 参数从 `sort=True` 改为 `sort=False`，保留应用内现有的坐标排序和文本块过滤。

| 方法 | 逐页完全一致 | 中位墙钟时间 | 中位 CPU 时间 |
|---|---:|---:|---:|
| 当前：PyMuPDF 排序 + 应用内坐标排序 | 612 / 612 | 5.112 秒 | 4.844 秒 |
| 候选：只做应用内坐标排序 | 612 / 612 | 5.121 秒 | 4.922 秒 |

文本完全一致，但候选墙钟中位数慢约 0.17%，CPU 中位数慢约 1.61%。变化落在环境波动范围内，没有稳定收益，故不合入。

## 交付决定

1. 不更改 0.4.19 生产源码；不提升版本号。
2. 继续以 0.4.17 作为回退比较基线，0.4.19 仍是源码候选，等待原 Harness 的真实模型对照与容器/平台验收。
3. 本轮没有新 Token 结论。离线实验分数不替代真实模型得分，也不与历史真实模型结果混算。
4. 只有出现能保持原文逐页一致、且端到端重复实测有稳定收益的单因素方案，才进入生产候选；否则保留当前正确性路径。
