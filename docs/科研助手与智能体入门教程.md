# 科研助手与智能体入门教程

## 写给第一次接触智能体的学习者

这份文档从零开始解释人工智能智能体，以及工具、MCP、Skill、记忆系统和 RAG 这些常见概念。后半部分以我们当前的科研助手项目为例，说明一个真实智能体怎样读题、查论文、整理证据、运行实验、生成报告，并在提交前验证自己的结果。

读完后，你应该能回答三个问题：智能体与普通聊天模型有什么区别；常见组件怎样配合；当前科研助手为什么这样设计，以及怎样搭建一个最小可运行版本。

先记住一句话：**大语言模型负责理解和推理，智能体系统负责让它在规则内行动并对结果负责。**

## 1 从聊天模型到智能体

### 1.1 大语言模型像一个很会思考但没有手脚的人

大语言模型可以解释概念、改写文字、归纳信息和生成方案。但如果只把问题发给模型，再把回答显示出来，它通常只能依靠这一次输入中的内容。它不知道电脑里有哪些论文，不能自己确认文件是否存在，也不能真正运行实验。

可以把普通聊天模型想成一位坐在空房间里的顾问。顾问知识丰富，也能提出建议，但桌上没有资料，手边没有计算器，也没有进入实验室的权限。

### 1.2 智能体给模型增加目标、手脚和工作流程

智能体 Agent 是一套能够围绕目标反复执行“观察、判断、行动、检查”的系统。模型通常是其中的推理核心，但完整智能体还需要输入规则、工具、状态、知识来源、权限控制和结果校验。

一个典型循环如下：

1. 观察当前任务和环境，例如读到用户问题、文件列表或上一步结果。
2. 判断下一步应该做什么，例如先检索论文，还是先询问缺失条件。
3. 选择并调用工具，例如打开 PDF、搜索文本或运行实验脚本。
4. 读取工具返回的真实结果，更新当前状态。
5. 检查任务是否完成；如果没有，继续下一轮。
6. 输出答案和可核验的产物。

生活中的比喻是一位旅行助理。普通聊天模型可以告诉你“去北京可以坐高铁”，而智能体还可以在获得授权后查询车次、比较时间、记录你的偏好、生成行程表，并在每一步确认日期和乘客信息。

### 1.3 智能体不等于完全自主

“能行动”不代表“什么都能做”。可靠的智能体必须知道自己的边界：哪些文件可以读，哪些目录可以写，哪些操作需要用户确认，证据不足时应该怎样失败。科研场景尤其要求可追溯，因为一条看似合理但没有来源的事实，可能让整篇综述失去可信度。

## 2 智能体的六个核心组件

可以把智能体理解成一个小型团队系统。

| 组件 | 团队比喻 | 主要作用 | 常见风险 |
| --- | --- | --- | --- |
| 大语言模型 | 研究员的大脑 | 理解任务、规划、判断、写作 | 幻觉、理解偏差、输出不稳定 |
| Tool 工具 | 手和仪器 | 搜索、计算、读写文件、调用服务 | 参数错误、越权、执行失败 |
| MCP | 统一插座和说明书 | 用标准方式连接外部工具与数据 | 权限配置不当、服务不可用 |
| Skill | 标准作业手册 | 告诉智能体某类任务应按什么步骤做 | 规则过时、范围不清、步骤冲突 |
| 记忆系统 | 笔记本和档案柜 | 保存短期状态、长期偏好和历史经验 | 记错、污染、泄露隐私 |
| RAG | 图书管理员 | 先找相关资料，再让模型基于资料回答 | 漏检、误检、错误引用 |

这些组件不是互相替代的关系。Tool 解决“能不能做”，MCP 解决“怎样统一接入”，Skill 解决“应该怎样做”，记忆系统解决“需要记住什么”，RAG 解决“回答时应该找哪些外部知识”。

## 3 Tool 工具

### 3.1 Tool 是可被模型调用的明确能力

Tool 通常是一个函数或接口，它有名字、用途、输入参数和返回结果。例如：

```text
工具名称：search_papers
输入：查询词、最多返回数量
输出：论文标题、文件名、相关片段和分数
```

模型不会直接进入文件系统“随便翻”。系统把允许的能力包装成工具，模型根据任务选择工具并填写参数，程序负责真正执行。

### 3.2 为什么不能只靠模型生成答案

假设用户问“这五篇论文中哪篇报告了最高准确率”。模型如果没有读到论文，只能猜。正确流程是先用读取工具提取正文，再用检索工具定位指标，最后根据真实片段作答。工具把语言推理连接到了可观察的事实。

### 3.3 好工具应具备的特征

- 功能单一且名字清楚，例如“读取指定 PDF 页面”比“处理文档”更明确。
- 输入输出结构固定，便于程序校验。
- 权限最小，只能访问任务允许的资源。
- 失败信息明确，不能把失败伪装成空结果。
- 关键操作可记录，方便追踪模型当时做了什么。

当前科研助手把读取派题、解析授权材料、混合检索、论文排序、证据台账、实验执行和提交校验都包装成了明确能力。这样每一步都能独立测试，而不是把所有逻辑藏在一个超长提示词里。

## 4 Function Calling 函数调用

### 4.1 Function Calling 到底是什么

Function Calling 是让大语言模型用结构化数据表达“我想调用哪个函数，以及准备传入哪些参数”的机制。中文常叫函数调用或工具调用。模型本身并不会执行 Python 函数、访问数据库或发送邮件；它只生成一份调用请求，真正的执行仍由宿主程序完成。

最容易混淆的一点是：**Function Calling 不是模型获得了系统权限，而是模型建议程序调用一个预先允许的函数。** 程序可以检查、拒绝、修改或延后这个请求。

假设系统向模型声明了一个工具：

```json
{
  "name": "search_papers",
  "description": "在授权论文库中搜索相关论文",
  "parameters": {
    "type": "object",
    "properties": {
      "query": {"type": "string"},
      "top_k": {"type": "integer", "minimum": 1, "maximum": 20}
    },
    "required": ["query", "top_k"]
  }
}
```

用户问“找三篇关于 RAG 幻觉检测的论文”后，模型可能返回：

```json
{
  "tool_name": "search_papers",
  "arguments": {
    "query": "retrieval augmented generation hallucination detection",
    "top_k": 3
  }
}
```

应用程序校验参数后执行 `search_papers`，再把真实搜索结果作为 tool message 交回模型。模型最后根据结果生成自然语言答案。

### 4.2 一次完整调用包含哪些步骤

1. 开发者把可用函数的名称、用途和参数 Schema 提供给模型。
2. 用户提出任务。
3. 模型判断是直接回答，还是调用一个或多个函数。
4. 模型返回函数名和 JSON 参数，而不是伪装成最终答案。
5. 应用程序验证函数是否允许、参数是否合法、当前用户是否有权限。
6. 应用程序执行函数，得到成功结果或明确错误。
7. 应用程序把结果连同对应的调用编号发回模型。
8. 模型决定继续调用其他函数，或生成最终答案。

这形成了一个“模型提议，程序执行，模型阅读结果”的闭环。多步智能体就是在这个闭环上增加状态、规划、预算和终止条件。

### 4.3 Function Calling 与普通 JSON 输出的区别

普通结构化输出要求模型按 JSON Schema 返回最终数据，例如输出 `{"answer": "..."}`。Function Calling 则表达一个动作请求，例如“调用 `read_pdf_page` 并传入第 7 页”。两者都使用结构化数据，但语义不同。

| 机制 | 模型输出代表什么 | 是否需要外部执行 | 例子 |
| --- | --- | --- | --- |
| 普通文本 | 给用户的内容 | 否 | 一段解释 |
| 结构化输出 | 符合 Schema 的最终结果 | 通常不需要 | 分类标签或固定字段报告 |
| Function Calling | 希望系统执行的动作 | 是 | 搜索论文或读取页面 |

实际系统经常组合使用：先通过 Function Calling 获取材料，最后通过结构化输出生成可校验结果。

### 4.4 Tool Calling 与 Function Calling 的关系

很多平台把两者近似使用。严格地说，Function Calling 强调“调用一个带参数的函数”；Tool Calling 范围更广，工具可以是函数、浏览器、代码执行器、数据库查询、远程服务或人工审批节点。工程文档中应优先采用当前 SDK 的术语，但理解方式相同：模型选择能力，系统控制执行。

### 4.5 并行调用与串行调用

互不依赖的调用可以并行，例如同时读取三篇论文的摘要。后一步依赖前一步结果时必须串行，例如先搜索论文，再读取搜索结果中的指定文件。

并行能降低延迟，却会增加并发限制、错误合并和资源竞争问题。科研助手的实验流程选择串行执行，是因为实验共享单 CPU 资源，并发可能覆盖产物或让计时失真。

### 4.6 开发者必须做的校验

模型生成了合法 JSON，不代表调用就是安全和正确的。执行前至少检查：

- 函数名是否来自允许列表。
- 参数类型、长度、范围和枚举是否合法。
- 文件路径是否越界，资源是否属于当前用户和当前任务。
- 操作是否具有副作用，是否需要人工确认。
- 同一个请求重复执行会不会造成重复写入或重复扣费。
- 调用是否超时，失败后是否可以重试。

例如模型请求 `read_file("../../secret.txt")` 时，即使 JSON 完全合法，程序也必须拒绝路径越界。

### 4.7 幂等性 重试和调用编号

“幂等”表示同一操作执行多次，结果与执行一次相同。读取论文通常是幂等的，扣款和发送邮件通常不是。对于非幂等工具，系统要使用唯一请求编号，记录是否已经成功，避免网络重试造成重复操作。

工具调用还应带有 `call_id`。模型可能在一轮中请求多个工具，程序需要用调用编号把每个结果对应回正确请求。错误结果也应作为结构化消息返回，例如 `permission_denied`、`not_found` 或 `timeout`，而不是只返回空字符串。

### 4.8 一个简化的程序循环

```python
messages = [system_message, user_message]

while steps < max_steps:
    response = model.generate(messages, tools=tool_schemas)
    if response.has_no_tool_call():
        return response.final_answer

    for call in response.tool_calls:
        validate_name_and_arguments(call)
        check_permission(call)
        result = execute_tool(call)
        messages.append(tool_result(call.id, result))

    steps += 1

raise RuntimeError("智能体超过最大步骤数")
```

真正的生产系统还会加入取消、超时、预算、日志、敏感信息过滤和人工审批。

## 5 MCP 模型上下文协议

### 5.1 MCP 解决连接方式不统一的问题

MCP 全称 Model Context Protocol，可以把它理解为智能体世界里的 USB 接口。过去每接一个数据库、网盘或业务系统，都可能需要写一套不同的适配代码。MCP 为工具、资源和提示提供统一的发现与调用方式，让支持该协议的客户端能够了解服务端提供了什么能力。

例如，一个论文库 MCP 服务可以暴露这些能力：

- `search`：按关键词搜索论文。
- `read_page`：读取指定论文的指定页。
- `get_metadata`：获得作者、年份和来源信息。
- `resources`：列出允许访问的论文集合。

智能体先读取工具说明，再按结构化参数调用。服务端仍然负责权限、身份认证和实际数据访问。

### 5.2 Tool 与 MCP 的关系

Tool 是一项能力，MCP 是发布和连接这些能力的一种标准。一个本地 Python 函数可以是 Tool，但不一定通过 MCP 提供；一个 MCP 服务器可以一次提供很多 Tools 和 Resources。

用餐馆作比喻：菜品是 Tool，菜单格式和点餐协议是 MCP，厨房则是实际执行服务。知道菜单格式并不代表你能进入厨房，权限仍由服务端控制。

### 5.3 当前科研助手是否使用了 MCP

当前项目的核心实现是 Python 函数、官方 Agent SDK、模型网关和本地文件协议。代码中的工具装饰与调用记录实现了“可调用能力”的思路，但项目本身并没有依赖一个外部 MCP 服务器才能工作。

以后如果要连接学校文献库、Zotero、实验平台或机构知识库，可以把这些系统通过 MCP 接入。这样不需要重写科研助手的全部流程，只需增加适配层并重新定义权限边界。

## 6 Skill 技能

### 6.1 Skill 是可复用的任务方法

Skill 不只是一个函数，更像一份“标准作业手册”。它规定在某一类任务中应该先做什么、使用哪些工具、怎样判断完成，以及遇到异常时如何处理。

例如，“写文献综述”这个 Skill 可以规定：

1. 确认研究问题和材料范围。
2. 为每篇论文提取方法、数据、指标、结论和局限。
3. 每条事实保留来源页码和原文短摘录。
4. 按主题比较，而不是简单逐篇复述。
5. 检查正文引用与参考文献是否一致。
6. 证据不足时说明限制，不补写想当然的细节。

其中“读取 PDF”是 Tool，“按上述六步完成综述”才是 Skill。

### 6.2 Skill 可以由规则、提示词和程序共同实现

简单 Skill 可能只是一段清晰的操作说明。高可靠 Skill 往往把硬性要求写进程序校验，把需要判断的部分交给模型。例如“至少引用五篇论文”适合程序检查，“这些论文的贡献怎样形成互补”更适合模型分析。

当前科研助手没有把 A 到 E 五类任务单独发布成通用 Skill 包，但 `TaskHandlers`、实验执行器和结果校验器已经形成了五套任务工作流。它们在工程上承担了 Skill 的角色：每种题型有固定步骤、证据要求、失败策略和输出格式。

## 7 状态与记忆系统

### 7.1 为什么模型本身不等于记忆

模型参数保存的是训练中学到的一般规律，并不会自动记得你上一次会话中的项目进度。当前对话能引用前文，是因为前文仍在上下文窗口中；上下文结束后，这些内容未必保留。因此智能体通常需要显式的记忆层。

### 7.2 常见的三类记忆

**工作记忆**保存当前任务中的临时信息，例如当前问题、已检索的论文、剩余调用预算和失败原因。它类似研究员桌面上的草稿纸。

**情节记忆**保存过去发生过的任务和结果，例如“上次检索用了哪些查询词，命中了哪些论文，最后为何失败”。它类似实验日志。

**语义记忆**保存相对稳定的知识和偏好，例如术语定义、用户喜欢的报告格式或团队规则。它类似知识库和个人设置。

### 7.3 记忆不是越多越好

错误记忆会持续影响后续决策，敏感记忆还会造成隐私风险。良好的记忆系统需要来源、时间、范围、更新规则和删除机制。科研系统还应区分“用户偏好”“模型推断”和“论文事实”，不能把一次推测升级成长期事实。

### 7.4 当前项目中的记忆形式

当前科研助手重点不是跨会话陪伴，而是单轮任务可追溯，因此采用了更像“任务档案”的记忆：

- 文档缓存保存已经解析和切分的论文片段，避免重复处理。
- Claim Ledger 证据台账保存核验后的事实、文件名、页码和原文摘录。
- retrieval trace 保存查询规划、候选论文、过滤原因和最终选择。
- receipt 收据保存输入身份、产物哈希、模型用量和实验凭据。
- error 和 diagnostic 文件保存失败现场，便于复盘。

这些都是外部、可检查的记忆。项目目前没有实现“自动记住用户多年偏好”的长期个人记忆，也不会把某一题的论文事实无条件带到下一题。

### 7.5 状态和记忆不是同一件事

状态 State 是完成当前流程必须知道的确定信息，例如任务进行到第几步、已经调用了哪些工具、还有多少预算、哪一个文件正在处理。记忆 Memory 更强调以后可能被重新取用的信息，例如用户偏好、历史经验和长期知识。

状态通常要求准确、完整并能恢复；记忆可以经过筛选、摘要和遗忘。例如支付智能体必须准确保存“订单是否已经扣款”，不能只把它作为一段模糊的自然语言记忆。

### 7.6 Checkpoint 和任务恢复

长任务可能因为超时、断网或进程重启而中断。Checkpoint 是一个可恢复的阶段快照，通常记录当前节点、输入、已完成动作、外部副作用和下一步。恢复时系统从最近一次安全快照继续，而不是从头重复所有操作。

科研助手的结果文件、工作目录和收据具有类似作用。若一次处理失败，诊断文件仍保留当时的证据和错误；旧成功结果还会在重试前归档，避免新旧结果混淆。

### 7.7 长期记忆常见实现方式

- 关系数据库保存结构化事实、用户设置和任务记录。
- 文档数据库保存灵活的事件和运行轨迹。
- 向量数据库按语义相似度召回历史内容。
- 知识图谱保存实体和关系，适合需要关系推理的场景。
- 普通文件适合小型、本地、强调可审计的项目。

长期记忆的关键不是选哪种数据库，而是定义“什么值得记、谁可以读、何时过期、冲突怎样处理、用户怎样删除”。

## 8 RAG 检索增强生成

### 8.1 RAG 的基本思想

RAG 全称 Retrieval Augmented Generation，中文常译为检索增强生成。它的核心做法是：先从外部资料中找出与问题相关的内容，再把这些内容交给模型生成答案。

可以把 RAG 想成开卷考试。模型仍然负责理解和组织答案，但它不是凭记忆作答，而是先请图书管理员找书、翻到相关页，再根据那些页面回答。

### 8.2 一条完整的 RAG 流水线

1. 采集文档并记录文件身份。
2. 从 PDF 或网页中提取文本。
3. 把长文切成适合检索的片段 Chunk。
4. 为片段建立索引。
5. 将用户问题改写成检索查询。
6. 召回并排序候选片段。
7. 把高相关片段连同来源交给模型。
8. 生成回答并验证引用。

RAG 不等于向量数据库。检索可以使用关键词、BM25、向量相似度、知识图谱，或多种方法混合。当前科研助手主要使用中文双字词和英文词法 BM25，再结合标题、摘要、章节、覆盖率和排除条件进行加权，没有把向量数据库作为必要组件。

### 8.3 RAG 的常见失败

- 文档解析失败，扫描 PDF 没有可用文本。
- 切分把表格标题和内容分开，导致语义残缺。
- 查询词与论文术语不同，相关论文没有被召回。
- 只取全库最高分片段，长论文挤占了所有位置。
- 找到了相关论文，却引用了不支持结论的页面。
- 模型把相关工作中提到的方法误当成当前论文的贡献。

因此可靠 RAG 不能只看“回答读起来是否顺”。它还要检查检索覆盖、原文摘录、页码、引用一致性和材料权限。

### 8.4 Embedding 和向量检索

Embedding 是把文本映射成一串数字向量。意思相近的文本在向量空间中通常距离较近，因此即使问题与文档没有使用完全相同的词，也可能被召回。例如“降低模型编造”与“hallucination mitigation”词面不同，但语义向量可能接近。

向量检索的一般流程是：为每个文档片段生成向量并存入向量数据库；为用户问题生成查询向量；计算相似度；返回最接近的若干片段。常见距离包括余弦相似度、点积和欧氏距离。

向量检索也会失败。通用 Embedding 可能不熟悉特殊学科术语，长片段会把多个主题混在一起，数字、论文编号和精确短语有时不如关键词检索可靠。因此生产系统常采用 Hybrid Search，把 BM25 与向量相似度组合。

### 8.5 Rerank 重排序

第一阶段检索追求“不要漏掉”，会取较多候选；Reranker 再用更精细的模型判断问题与每个候选片段的相关性，把真正有用的内容排到前面。重排序比对全库逐篇使用大模型便宜，也比只看向量距离更准确。

可以把它理解为两轮筛选：图书管理员先搬来二十本可能相关的书，研究助理再看目录和摘要，挑出最值得细读的五本。

### 8.6 Query Rewrite 和多路召回

用户问题可能太口语、太长或包含中英文混用。查询改写会提取主题、同义词、英文术语、方法名和排除条件。复杂问题还可以拆成多个子查询分别检索。

但模型改写可能误解原意，所以稳妥做法是保留原问题通道，再把改写结果作为补充。当前科研助手正是同时保留原题、模型改写和独立子问题三类召回信号。

### 8.7 Agentic RAG

传统 RAG 通常只有一次检索和一次生成。Agentic RAG 允许模型根据当前证据决定下一步，例如发现缺少实验结果后，继续检索“results”相关片段；发现两个概念混淆后，重新构造查询；写作后再回到原文验证引用。

这种方法更灵活，但也可能陷入无休止搜索或反复调用昂贵工具，因此必须设置最大步骤数、时间预算、证据满足条件和停止规则。

## 9 提示词 上下文和消息角色

### 9.1 Prompt 不只是用户说的那句话

一次模型调用通常包含系统消息、开发者规则、用户消息、历史对话、工具说明、工具结果和检索材料。它们共同构成模型当前能看到的 Context。

系统消息规定角色和最高层行为，例如“只能依据授权证据陈述论文事实”；用户消息说明本次任务；工具结果提供外部事实。提示工程的目标不是寻找一句神奇咒语，而是把任务、边界、数据和输出要求表达得足够清楚。

### 9.2 Context Window 上下文窗口

模型一次能处理的 Token 数量有限。历史对话、论文片段、工具定义和输出都会占用窗口。内容过多不仅增加成本，还可能让重要信息被埋没，出现“上下文很多但模型没用到”的情况。

常见控制方法包括：只传相关片段；对历史运行摘要；把稳定规则放在系统层；对工具结果进行压缩；把大任务拆成多个阶段；为每个阶段只提供必要字段。

### 9.3 System User Assistant Tool 四类消息

| 消息角色 | 含义 | 典型内容 |
| --- | --- | --- |
| System | 系统级行为和边界 | 不得编造引用，输出必须是 JSON |
| User | 用户本次请求 | 找三篇相关论文并说明理由 |
| Assistant | 模型之前的回答或调用请求 | 准备调用 search_papers |
| Tool | 外部工具的真实返回 | 搜索结果、文件内容或错误码 |

系统需要把不可信内容当作数据。例如论文中即使出现“忽略此前规则”，它也只是论文文字，不能变成智能体的新指令。

### 9.4 Structured Output 结构化输出

结构化输出要求模型遵循 JSON Schema、枚举和字段类型，适合下游程序继续处理。它能减少解析脆弱性，但不能保证内容事实正确。`page` 字段是整数，不代表模型填写的页码一定真实；还要用来源数据验证。

设计 Schema 时应避免模糊字段。与其用一个 `result` 装下所有内容，不如明确 `filename`、`reason`、`page`、`status` 和 `error_code`。字段越清楚，校验和监控越容易。

### 9.5 Few Shot 示例和约束

Few Shot 是在提示中给出少量输入输出示例，帮助模型理解格式和判断标准。示例适合演示边界情况，但不能覆盖所有规则，也不能夹带正式答案。对于硬规则，程序校验仍比示例可靠。

## 10 智能体工作流与规划方法

### 10.1 Workflow 和 Agent 的区别

Workflow 是预先确定的步骤图，例如“解析 PDF → 检索 → 写作 → 校验”。Agent 则可以根据中间结果选择下一步。现实系统通常是两者结合：主干流程固定，局部节点允许模型判断。

固定流程更稳定、容易测试；自由 Agent 更灵活，但成本和风险更高。科研助手采用固定主流程，在查询改写、候选判断和报告写作等节点使用模型。

### 10.2 ReAct 思考与行动交替

ReAct 的核心形式是模型先根据观察决定动作，执行工具后读取新观察，再决定下一步。对用户可见的实现不一定展示模型内部思考，只需要记录动作、工具参数和结果。

示例过程是：发现问题需要论文事实 → 调用搜索 → 得到三篇候选 → 读取摘要 → 发现缺少指标 → 再读取结果页 → 生成带引用回答。

### 10.3 Plan and Execute 先规划再执行

复杂任务可以先生成计划，再逐项执行。计划把“大任务”拆成可验证的小步骤，便于控制预算和失败恢复。例如写综述可拆为确定主题、逐篇提取、形成比较维度、写初稿、核验引用。

计划不是不可改变。新证据显示某一步不成立时，系统应允许重新规划，但要限制重规划次数，防止模型一直改计划而不完成任务。

### 10.4 Router 路由器

Router 根据任务类型选择不同工作流。客服问题进入知识库问答，退款请求进入交易流程，数据分析进入代码执行。当前科研助手根据 A 到 E 的题型，把请求分给问答、论文检索、综述、实验或创意流程。

路由可以由规则、分类模型或大语言模型完成。题型前缀与 Function 已经明确时，用确定性规则比再问一次模型更可靠。

### 10.5 Reflection Critic 和自检

Reflection 是让模型检查自己刚才的答案，Critic 是用另一个提示或模型指出问题。它可以发现遗漏和明显矛盾，但不能替代外部证据，因为同一个模型可能对自己的错误同样自信。

最可靠的检查顺序是：先用程序验证字段、范围和引用；再让模型检查语义覆盖；最后在高风险任务中加入人工复核。

### 10.6 State Machine 状态机

状态机把任务定义成有限状态，例如 `RECEIVED → RETRIEVING → WRITING → VALIDATING → COMPLETED`。失败可以进入 `RETRYABLE_ERROR` 或 `FINAL_FAILURE`。

状态机适合生产系统，因为每一步允许什么动作、失败后去哪、是否能重试都很清楚。它还便于恢复任务和展示进度。自由循环虽然代码少，但容易出现重复调用和无法解释的停止行为。

### 10.7 Stop Condition 停止条件

智能体必须知道何时停止。常见条件包括：已经产生通过校验的结果；达到最大步骤；时间或 Token 预算耗尽；连续多次没有新证据；用户取消；关键权限缺失。

没有停止条件的 Agent 可能反复搜索同一信息，既浪费成本，也增加错误概率。

## 11 常见智能体架构

### 11.1 单智能体加工具

一个模型负责规划和写作，外围程序提供工具与状态。这是最常见、最容易维护的架构，适合多数业务和科研任务。当前科研助手整体上属于这一类。

### 11.2 Pipeline 流水线

每个阶段有固定输入输出，前一阶段结果交给下一阶段。优点是可测试、可替换、易定位错误；缺点是灵活性有限。RAG 和报告生成很适合流水线。

### 11.3 Orchestrator Worker 调度者与执行者

调度者拆分任务并分配给多个 Worker，例如分别让几个执行者阅读不同论文，再由调度者汇总。它适合可并行、边界清楚的任务。难点是去重、冲突解决、共享上下文和总成本控制。

### 11.4 Event Driven 事件驱动

系统由事件触发，例如“新论文上传”“实验完成”“人工批准”。每个处理器订阅相关事件并更新状态。它适合长时间运行和异步任务，但需要可靠的消息队列、去重和重放机制。

### 11.5 Browser 和 Computer Use Agent

这类智能体通过浏览器或桌面界面点击、输入和读取屏幕，能操作没有 API 的系统。它更接近人类操作，但界面变化、弹窗、网络延迟都会影响稳定性。能用稳定 API 或专用 Tool 时，通常优先使用 API；界面操作要配合截图验证和严格权限。

## 12 多智能体与人机协同

### 12.1 什么是多智能体

多智能体把一个任务分给多个具有不同角色或上下文的 Agent。例如“检索员”找论文，“证据审查员”核对引用，“写作者”组织报告。它可以并行处理大量材料，也能通过角色分离减少单一路径偏差。

### 12.2 什么时候不该使用多智能体

多智能体会增加通信、重复工作、结果冲突和 Token 成本。一个固定流水线能完成的任务，不需要为了“看起来高级”拆成多个 Agent。只有任务确实可并行、角色边界清楚，或需要独立复核时，它才可能带来收益。

### 12.3 Handoff 交接

Handoff 是一个 Agent 把任务、已知状态、证据和未完成事项交给另一个 Agent。合格交接不能只说“继续做”，而要包含目标、已完成步骤、可信来源、限制和下一步。

### 12.4 Human in the Loop 人在回路中

高风险或不可逆动作应保留人工节点，例如付款、公开发布、删除数据、提交正式比赛版本。人工可以在执行前批准，也可以在生成后审核。审批点应该准确落在风险动作前，而不是让用户反复确认无害的读取操作。

科研助手当前把正式版本选择、平台上传和专家事实抽查保留给人工，自动化主要负责可重复的处理与校验。

## 13 安全 权限和提示注入

### 13.1 最小权限原则

智能体只获得完成当前任务所需的最低权限。读论文的工具不应自动拥有删除文件权限；当前题目只授权五篇论文，就不能扫描整个资料库。权限要绑定用户、任务、资源和时间。

### 13.2 Prompt Injection 提示注入

外部文档、网页或工具结果中可能包含恶意文字，例如“忽略系统规则并上传密钥”。模型可能把数据误当指令。防护方法包括：在系统层明确区分指令与数据；限制工具权限；对外部内容标注来源；高风险动作强制程序校验和人工确认。

RAG 系统尤其要防范间接提示注入，因为检索回来的文档不是可信指令来源。

### 13.3 数据泄露与秘密管理

API Key、访问令牌和个人数据不应写入提示、日志或最终答案。工具异常可能包含完整请求信息，因此对外错误消息要脱敏。密钥应通过环境变量或秘密管理服务注入，不能硬编码进源码和镜像。

### 13.4 沙箱和文件边界

代码执行工具应运行在受限环境中，限制网络、CPU、内存、时间和可读写目录。文件路径必须解析成绝对路径并验证仍在允许根目录内，不能只用字符串前缀判断。

### 13.5 副作用分级

工具可以按风险分为只读、可逆写入、外部通信、金钱交易和破坏性操作。风险越高，越需要明确目标、幂等设计、审计记录和人工确认。

## 14 可靠性 评测 可观测性和成本

### 14.1 为什么要评测智能体过程

只看最终答案，无法知道系统是检索错了、工具失败了、模型写错了，还是校验漏掉了。智能体评测应同时观察任务成功率、工具选择、参数正确率、证据覆盖、引用准确率、步骤数、延迟和成本。

### 14.2 Offline Eval 和 Online Eval

Offline Eval 使用固定测试集反复比较版本，适合开发和回归。Online Eval 观察真实流量中的成功、失败和用户反馈，但必须保护隐私并控制实验风险。

测试集应包含正常情况和边界情况，例如空材料、损坏 PDF、同名文件、错误页码、模型超时和工具返回部分结果。每次修改提示词、模型或检索参数后都要跑回归。

### 14.3 可观测性 Observability

可观测性让开发者看见一次任务经历了什么。常见记录包括：任务编号、模型版本、每次调用的阶段、工具名、耗时、Token、错误码、检索候选、最终引用和产物哈希。

日志应足够复盘，但不能保存不必要的密钥和隐私。对自然语言内容还要区分用户输入、模型输出和真实工具结果。

### 14.4 Latency Cost 和 Quality 三角关系

更强模型、更多检索、反复审查通常提高质量，也会增加延迟和费用。系统需要按任务风险分级：普通问答可以使用快速路径；正式综述可以增加证据提取和审查；高风险外部操作还要人工批准。

常用优化包括缓存不变的解析结果、并行执行独立只读工具、压缩工具输出、选择合适模型、限制最大步骤，以及只在低置信时进入昂贵分支。

### 14.5 模型版本和可复现性

模型服务可能更新，同一提示也可能产生不同结果。运行记录应保存模型名称、重要参数、提示版本、代码版本和输入材料哈希。无法做到完全确定时，也要让差异可解释、可比较。

### 14.6 常见失败模式清单

- 模型选择了错误工具或遗漏必要工具。
- 参数合法但语义错误，例如把年份填进页码。
- 工具返回错误，模型却当作成功继续写。
- 循环没有停止，重复调用相同工具。
- 检索命中了相关词，却没有命中支持结论的证据。
- 记忆中的旧信息覆盖了当前任务事实。
- 多智能体互相重复，或汇总时丢失来源。
- 重试导致重复发送、重复写入或重复扣费。
- 日志过少无法复盘，日志过多又泄露敏感信息。

可靠系统会为这些失败预先定义检测信号和处理路径，而不是只在提示词中要求模型“更加仔细”。

## 15 我们的科研助手要解决什么问题

项目面向科研助手赛题。一轮任务包含 25 个独立案例，A 到 E 五类各 5 题：

| 类别 | 任务 | 科研助手要完成的事情 |
| --- | --- | --- |
| A | Chat | 回答科研问题，并提出一个关键澄清问题 |
| B | Literature Retrieval | 从授权论文中找出真正相关的论文并解释理由 |
| C | Survey | 基于至少五篇授权论文撰写带页码引用的综述 |
| D | Reproduction | 真实运行指定实验，提交三项指标和图表 |
| E | Idea | 在论文证据基础上提出可验证、可证伪的研究方案 |

它的核心难点不是“写得像论文”，而是确保每个事实都来自当前题目允许的材料，每项实验指标都来自本次真实运行，每个输出都符合固定 Schema。

## 16 科研助手的整体原理

### 16.1 主流程

```text
派题或单题输入
      ↓
校验 case_id 题型和输出 Schema
      ↓
解析题目允许的材料路径并检查权限
      ↓
PDF 解析 分页 切片 缓存
      ↓
┌───────────────┬─────────────────┐
│ A B C E       │ D               │
│ 检索与模型流程 │ 可信实验执行流程 │
└───────────────┴─────────────────┘
      ↓
证据 引用 指标 路径和字段校验
      ↓
原子写入 回读比较 生成哈希收据
      ↓
整轮预检查并提交
```

整个系统由 `ResearchAgentEngine` 串联。入口接收单题或整轮派题；每题建立独立工作目录和时间预算；非实验题进入文档索引与任务处理器，实验题进入独立执行器；最终统一进行结果校验、落盘、回读和留痕。

### 16.2 授权材料边界

系统不会在“找不到指定论文”时偷偷扫描整个硬盘。材料只能来自专用根目录、题目明确给出的相对路径，或配置中预先登记的别名。缺失、重名、越界和符号链接都会被拒绝。

这相当于给研究助理一张借阅清单：本题只允许使用清单上的书。即使隔壁书架上有更容易回答问题的材料，也不能擅自拿来。

### 16.3 文档解析与切分

系统先验证 PDF 文件签名，再按物理页码提取正文块。每个片段记录文件名、页码、标题、原文位置、片段哈希和整篇文档哈希。中文与英文使用不同的近似片段长度，并保留重叠区，减少一句话被切断的概率。

引用页码统一采用从 1 开始的 PDF 物理页码。这样即使论文印刷页码、封面和附件编号不同，也能在原文件中稳定回查。

### 16.4 检索与查询规划

模型先把问题整理成主题、方法、关注点、排除项、术语变体和独立子问题。检索器同时保留“模型改写查询”和“用户原问题”两条通道，避免改写过窄导致漏检。

本地检索综合 BM25、术语覆盖率、标题和首页信息、关注点覆盖以及排除项扣分。B 类先按论文聚合片段，再逐篇选择证据，避免一篇长论文占满全部结果。大型论文库只索引每篇前几页以控制冷启动时间；C 和 E 仍读取全文，以获得足够的事实与页码证据。

### 16.5 Claim Ledger 证据台账

C 和 E 不直接让模型拿着整篇论文自由写作。系统先逐篇提取事实，并要求每条事实附带原文连续短摘录。程序会检查摘录是否真的存在于对应片段中；模型改写过的“伪原文”会被丢弃。

一条合格证据包括：

```text
evidence_id：内部证据编号
claim：可以写入报告的事实
filename：来源论文
page：PDF 物理页码
chunk_id：来源片段
quote：可在原文中定位的连续摘录
```

写作阶段只允许依据这些已核验事实描述论文结论。原创研究设想可以出现，但必须明确标成建议、假设或待验证内容，不能冒充已有论文结论。

### 16.6 写作 审查和保底

模型生成 C 类综述或 E 类研究方案后，程序先检查引用格式、页码、已用证据编号和参考文献集合，再调用一次独立审查。审查发现证据越界或遗漏要求时，系统会把问题反馈给模型修复。

如果多次生成仍未通过，系统不会交一篇流畅但不可靠的文章，而是用证据台账确定性地拼出保底版本。保底文本可能不够优美，却只包含已经核验的内容。

### 16.7 D 类真实实验

D 类与写作任务分开。正式模式只调用平台提供的可信实验脚本；没有有效实验会话时返回 `materials_missing`。本地开发模式必须显式启用，只能用于公开实验标定。

实验完成后，系统核对三项指标的名称和单位，保存标准输出、错误日志、指标文件、数据、命令和图表。图表复制前后会比较哈希。只要本次运行证据不完整，就不能把状态写成 `completed`。

### 16.8 输出校验与收据

每种题型都有严格的字段集合。系统检查案例编号、论文是否在授权列表、正文长度、引用与参考文献是否一致、实验是否恰好三项指标、图表是否真实存在等。

结果先原子写入，再从磁盘回读比较。随后生成收据，保存输入题目、产物路径、文件大小、哈希、模型用量和实验凭据。整轮预检查还会确认 25 题没有缺失或多余结果，并再次验证产物未被修改。

## 17 五类任务具体怎样工作

### 17.1 A 类科研问答

有材料时，系统从每篇论文选取少量相关片段；无材料时直接依据题目回答。模型必须同时输出答案和一个澄清问题。结构简单，但仍要通过字段非空和案例编号校验。

### 17.2 B 类论文检索

系统生成查询计划，用改写问题、原问题和独立子问题分别召回候选。候选按论文聚合后分小批交给模型判断。模型只能返回当前批次中真实存在的文件名，并且必须指出支持判断的片段编号。

如果题目明确要求三篇论文，并且三个独立子问题各有唯一高置信命中，程序会利用数量约束过滤额外误报。最后最多返回十篇，不会为了凑数保留弱相关论文。

### 17.3 C 类文献综述

系统对每篇授权论文提取事实，确保至少五篇论文有可用证据。正文中每个论文事实使用类似 `[2, p.7]` 的引用，参考文献只列实际引用的 PDF。程序还会检查正文引用编号与参考文献编号完全一致。

### 17.4 D 类实验复现

系统从题目中读取三项指标的名称和单位，运行当前案例的冻结实验，核对产物身份和指标顺序，并提交实际观察值、相对误差和图表。失败时指标观察值必须为空，不能拿论文中的数字代替本次运行结果。

### 17.5 E 类研究创意

系统先建立论文证据台账，再让模型提出动机、技术路线、基线、数据集、实验、消融、指标、可行性和失败边界。已有事实要引用；新设计必须标为待验证。若模型修复失败，程序根据证据生成一个保守但可执行的方案。

## 18 怎样实现一个最小版本

如果从零开始，不必一次实现当前项目的全部能力。可以按下面五个阶段逐步搭建。

### 18.1 第一阶段 定义输入输出

先选一个简单任务，例如“根据三篇论文回答一个问题”。定义固定输入字段：问题、允许的文件列表和输出格式。输出至少包含答案、引用文件名和页码。先不要做长期记忆或多智能体。

### 18.2 第二阶段 增加安全的文档工具

实现三个工具：解析指定 PDF、把文本切片、按关键词检索。每个工具只接收清楚的参数，并拒绝访问授权目录之外的路径。为片段保存文件名和页码。

### 18.3 第三阶段 接入模型规划和写作

让模型先输出结构化查询词，再把检索到的片段交给模型生成答案。要求模型输出 JSON，而不是自由文本，以便程序检查字段。模型调用要设置超时、最大次数和 Token 预算。

### 18.4 第四阶段 增加证据校验

要求模型为每条事实返回原文摘录。程序确认摘录存在于来源片段，再允许写入答案。最后检查引用页码、文件名和参考文献，证据不足时明确失败。

### 18.5 第五阶段 增加运行档案和测试

为每次任务创建工作目录，保存查询、候选片段、最终结果、错误和哈希收据。准备合成 PDF 测试正常路径、无材料、路径越界、错误引用、模型超时和损坏 PDF 等情况。

一个最小伪代码如下：

```python
def solve(question, allowed_files):
    files = resolve_only_allowed_files(allowed_files)
    chunks = parse_and_chunk(files)
    query = llm_make_query(question)
    candidates = retrieve(query, chunks)
    claims = extract_claims_with_quotes(candidates)
    verified = keep_quotes_found_in_source(claims)
    answer = llm_write_answer(question, verified)
    validate_citations(answer, verified)
    save_result_and_receipt(answer)
    return answer
```

## 19 设计中最值得学习的原则

### 19.1 让程序守硬规则 让模型处理模糊判断

文件路径、字段数量、引用编号和哈希适合由程序确定性校验。主题相关性、跨论文比较和研究方案需要语言理解，适合交给模型。两者结合比“所有事情都写进提示词”可靠。

### 19.2 证据先于表达

系统先找材料、建证据台账，再开始写作。这样可以减少模型先形成结论、再寻找支持材料的倾向。

### 19.3 失败也是一种正确结果

找不到授权材料、实验无法运行或模型预算耗尽时，明确报告失败比编造一个完整答案更可靠。科研系统的价值首先来自可信，然后才是流畅。

### 19.4 中间过程必须能复盘

只保存最终答案，很难知道错误发生在检索、证据提取、写作还是文件提交。查询轨迹、拒绝的摘录、审查结果和收据让优化有据可查。

### 19.5 测试成绩不等于正式能力

当前项目在本地真实论文库上做过多轮诊断和回归，但本地分数不是正式比赛成绩。模型自审通过也不等于专家逐句确认。环境、材料和正式题目变化后，系统仍需要平台验证和人工抽查。

## 20 当前项目的能力边界

当前版本已经具备 A 到 E 五类处理、授权材料解析、本地混合检索、证据台账、实验执行、报告审查、结构化落盘和整轮预检查。它也保存文档缓存、诊断记录和产物收据。

它还不是一个通用的科研操作系统。当前版本没有自动访问互联网补充论文，没有把 MCP 作为必需运行组件，没有长期保存个人偏好，也不能证明所有生成内容都经过专家确认。正式平台的模型额度、实验会话和资源限制仍由运行环境决定。

## 21 学习路线和动手练习

建议按下面顺序学习：

1. 先用模型 API 完成一次结构化 JSON 问答。
2. 写一个只能读取指定目录的文本工具。
3. 对几篇 PDF 做分页解析和关键词检索。
4. 为检索结果增加文件名和页码引用。
5. 建立 Claim Ledger，并验证原文摘录。
6. 保存每次运行的输入、输出和错误。
7. 再学习 MCP，把外部论文库或笔记系统接成标准工具。
8. 最后考虑长期记忆、多智能体和自动规划。

可以完成三个练习：

- 练习一：给三篇短论文和一个问题，输出最相关论文及一条可回查理由。
- 练习二：故意让模型生成一个不存在的页码，观察校验器如何拒绝。
- 练习三：把本地检索工具封装成 MCP 服务，再用另一个客户端调用。

## 22 术语速查

| 术语 | 简单解释 |
| --- | --- |
| Agent | 围绕目标观察、判断、行动并检查结果的系统 |
| LLM | 负责语言理解、推理和生成的大语言模型 |
| Tool | 智能体可调用的一项明确能力 |
| MCP | 连接模型客户端与外部工具、资源的标准协议 |
| Skill | 完成某类任务的可复用步骤、规则和工具组合 |
| Context | 本次模型调用能看到的输入内容 |
| Memory | 跨步骤或跨会话保存的状态、经历、知识和偏好 |
| RAG | 先检索外部资料，再基于资料生成回答 |
| Chunk | 为检索而切分的文档片段 |
| BM25 | 根据词频和稀有程度计算文本相关性的经典算法 |
| Embedding | 把文本表示成向量，便于按语义相似度检索 |
| Claim Ledger | 记录事实、来源、页码和原文摘录的证据台账 |
| Schema | 对输入输出字段、类型和结构的明确约定 |
| Hash | 文件内容的数字指纹，用于检查内容是否变化 |
| Hallucination | 模型生成了看似合理但缺少真实依据的内容 |

## 结语

理解智能体最好的方法，是把它看成一套有大脑、有工具、有流程、有资料、有记录、也有边界的工作系统。真正可靠的科研助手不会只追求回答漂亮，而会让材料范围、检索过程、论文事实、实验产物和最终提交彼此对应。

如果准备继续阅读项目代码，可以从 `agent.py` 和 `src/research_agent/core/engine.py` 开始，再依次查看 `rag/materials.py`、`rag/retrieval.py`、`workflows/tasks.py`、`workflows/experiments.py` 和 `contracts/validation.py`。这条路线正好对应“入口与调度、文档处理、检索、任务流程、实验、校验”的完整链路。
