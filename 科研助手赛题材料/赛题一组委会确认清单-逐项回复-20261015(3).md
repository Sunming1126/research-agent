# 赛题一（科研助手）待确认问题逐项回复

回复对象：参赛队伍  
核查日期：2026-10-15  
对应原文：《赛题一（科研助手）待确认问题清单》（2026-10-11）

本文根据核查当日云端平台源码、运行中 API 容器及实际配置整理，可作为组委会回复参考。说明的是当前平台接入行为，不另行变更评分规则。基础镜像内置的通用 SDK 默认值，不等于赛题一运行时协议。

## 一、`/solve` 报文契约与评分读取位置

### 1. 平台实际发送八字段题目 JSON，还是 `TaskRequest`？

**平台实际发送八字段原始题目 JSON，不使用通用 SDK 的 `TaskRequest` 包装。**

请求形式如下，示例内容仅用于说明结构：

```json
{
  "case_id": "C-01",
  "function": "Survey",
  "title": "示例题目",
  "input": "本题具体要求",
  "materials": ["指定论文.pdf"],
  "constraints": ["本题约束一", "本题约束二"],
  "expected_output": "本题输出要求",
  "output_schema_ref": "Survey"
}
```

其中 `input` 是字符串，`constraints` 是字符串数组；它们不是通用 SDK 的对象类型 `input` 和 `Constraints`。

因此，直接沿用要求 `task_id` 和对象类型 `input` 的通用 HTTP 路由，可能返回 HTTP 422。参赛者需要在自己的镜像中适配赛题一 HTTP 入口，直接接收上述题目，不能仅依赖基础镜像默认路由。

基础镜像提供开发依赖与 SDK，不表示内置通用路由已经自动适配所有赛题。

**补充：**

POST /solve` 原始正文为完整八字段 JSON：

```json
{
  "case_id": "A-01",
  "function": "Chat",
  "title": "仅演示协议的题目",
  "input": "本题实际要求",
  "materials": [],
  "constraints": [],
  "expected_output": "本题实际交付要求",
  "output_schema_ref": "Chat"
}
```

此示例只有字段结构，不是可以替代平台 assigned 文件的题目。请求必须与已派发的本题一致。

| 内容           | 当前默认位置/行为                                     | 依据或限制                           |
| ------------ | --------------------------------------------- | ------------------------------- |
| 派题           | `/output/data/<team>/dispatch.json`           | 平台反馈确认；校验 v2、25 题、各类五题、元数据与摘要。  |
| 当前题目         | `/output/data/<team>/assigned/<case_id>.json` | Single 只读取当前题，核对文件哈希和请求一致性。     |
| 论文           | `/data/papers`                                | 当前接入文档明确；本地可显式设置 `PAPERS_PATH`。 |
| 正式答案         | `/output/data/<team>/<case_id>.json`          | 只含本题字段，UTF-8 JSON 对象。           |
| C/E Markdown | `/output/data/expert/` 下按官方命名                 | 与 JSON 的 markdown 完全一致。         |
| D 图片         | `/output/data/figure/<team>/`                 | 仅列真实存在的图片，相对路径写入答案。             |
| 工作证据         | 本队 `work/<case>/<run>/` 等受控位置                 | 保存账本、诊断、运行记录；不伪造官方证据。           |

`<team>` 优先使用 `RESEARCH_WORKSPACE_TEAM`，其次本地 `TEAM_NAME`，最后为默认显示名。题目文件和允许材料只读；目录不明时使用明确配置或向平台核实，不扫描其他队伍及私有评分资料。

### 2. 八字段是否整体放在 `input`？`task_id` 是否等于 `case_id`？

**不会把八字段整体放进 `input`，请求体也不另外添加 `task_id`。**

- 题目身份使用正文中的 `case_id`，响应必须原样回显。
- 平台另在 `Idempotency-Key` 和 `X-Research-Task-ID` 请求头传入稳定的传输任务 ID；它是独立生成的 UUID，不等于 `case_id`。
- 平台发送 `X-Challenge-Protocol: research-assistant.v1` 标识本协议。
- `CHALLENGE_SESSION_ID` 是模型调用的会话标识，也不应与 `case_id` 或传输任务 ID 混为一谈。

若参赛者内部希望继续使用 SDK 的 `TaskRequest`，可在自有入口内自行转换；这只是 Agent 内部实现，不改变平台线上报文。

### 3. 五类结果应该放在 `output` 的哪些键？

**不放进通用 `output` 包装；应直接返回该类结果 JSON。** 当前顶层字段要求如下：

| 任务类型                     | 直接响应的顶层字段                                |
| ------------------------ | ---------------------------------------- |
| A：`Chat`                 | `case_id`、`answer`、`clarifying_question` |
| B：`Literature_Retrieval` | `case_id`、`papers`                       |
| C：`Survey`               | `case_id`、`path`、`markdown`              |
| D：`Reproduction`         | `case_id`、`status`、`metrics`、`figures`   |
| E：`Idea`                 | `case_id`、`path`、`markdown`              |

例如，C 类应返回：

```json
{
  "case_id": "C-01",
  "path": "data/expert/C-01-综述-<workspace_team>.md",
  "markdown": "本题完整的 Markdown 正文"
}
```

`<workspace_team>` 必须替换为运行时 `RESEARCH_WORKSPACE_TEAM` 的值，不能直接使用展示队伍名或 `TEAM_ID`。

不要把整个结果转成字符串放进 `output.answer`。不要额外添加通用的 `task_id`、`output`、`metadata`，也不要给非 D 类结果额外添加 `status`；平台按各类字段集合严格检查。

目前平台仅为部分适配器保留 `{"status":"success","payload":{...}}` 或 `{"status":"success","result":{...}}` 的显式解包兼容。通用 `TaskResponse.output` 不在该兼容范围内，新开发应统一采用直接 JSON，不依赖兼容包装。

**补充：**

| 类别                       | 直接响应与答案文件的顶层字段                          | 易错事项                                    |
| ------------------------ | --------------------------------------- | --------------------------------------- |
| A / Chat                 | `case_id, answer, clarifying_question`  | 后两项非空；不加 function/status，不返回字符串或围栏。     |
| B / Literature_Retrieval | `case_id, papers`；每篇 `filename, reason` | 完整且实际存在的 PDF 文件名；去重、排序、理由；              |
| C / Survey               | `case_id, path, markdown`               | 正文至少 800 字符；可追溯页码；有完整文件名参考表。            |
| D / Reproduction         | `case_id, status, metrics, figures`     |                                         |
| E / Idea                 | `case_id, path, markdown`               | 覆盖研究问题、方案、实验、指标、瓶颈、互补和可行性；不把模拟观察写成论文结果。 |

执行链路为：原始八字段 HTTP → SDK 请求适配 → 本队 dispatch/assigned 哈希核验 → `@tool` 记录业务操作 → 真实材料处理/模型生成或实验 helper → Schema 与证据检查 → 授权落盘和回读 → 直接题型对象响应。

`GET /health` 只检查服务状态，不执行完整任务。原始请求非法为 HTTP 422，执行失败和超时由当前适配层返回 500/504；这是当前工程错误映射，不应在官方未明确时说成冻结错误协议。

### 4. 评分读取响应体还是磁盘结果 JSON？

**两者都会使用，但职责不同。只返回 HTTP 或只写文件，都不能代替完整交付。**

1. 平台检查 HTTP 响应是否为合法 JSON，字段、题号及任务类型是否符合协议。
2. 平台检查 `/output/data/<workspace_team>/<case_id>.json` 是否存在，并与响应结果一致。
3. C/E 类还会检查 `path` 指向的 Markdown 文件与响应 `markdown` 一致；D 类检查要求的图表等产物。
4. 本题 Agent 停止后，平台封存结果文件，再把封存工作区交给官方判题器。最终内容评分依据封存文件及相关产物、裁判判断和适用的平台证据，不采信选手自报分数。

路径要区分：JSON 内 `path` 使用相对路径，例如 `data/expert/...md`；容器实际写入位置为 `/output/data/expert/...md`。

## 二、模型接口环境变量组

### 1. 运行时实际注入哪一组变量？

**平台同时注入推荐变量与兼容变量。应以容器启动时实际获得的值为准。**

| 用途          | 推荐变量                     | 当前兼容变量                                  |
| ----------- | ------------------------ | --------------------------------------- |
| 模型 Base URL | `CHALLENGE_LLM_BASE_URL` | `PLATFORM_LLM_URL`                      |
| API Key     | `CHALLENGE_LLM_API_KEY`  | `PLATFORM_API_KEY`                      |
| 模型名称        | `CHALLENGE_LLM_MODEL`    | `PLATFORM_LLM_MODEL`、`AGENT_MODEL_NAME` |
| 模型会话标识      | `CHALLENGE_SESSION_ID`   | 不应以 `TEAM_ID` 替代                        |

基础镜像 `ENV` 中没有列出 `CHALLENGE_*`，不代表平台运行时没有这些变量；平台在创建评测容器时追加注入。

模型调用应读取上述值，并携带：

```text
Authorization: Bearer <运行时 API Key>
X-Session-ID: <CHALLENGE_SESSION_ID>
```

按注入的 Base URL 构造 OpenAI-compatible 请求，避免重复拼接 `/v1`。不要硬编码模型服务地址、模型名称或密钥，不要修改带有平台会话路由信息的地址，也不要把完整密钥或会话路由写入公开日志。

`TEAM_ID` 用于平台队伍身份与遥测关联；结果目录使用 `RESEARCH_WORKSPACE_TEAM`，二者用途不同。

模型调用数和 Token 用量以平台受保护的 Gateway 审计为准，不以 Agent 自报的 `metadata` 为准。

## 三、遥测（OTLP）的注入与影响

### 1. 平台是否注入 OTLP endpoint，变量名是什么？

**会。当前实际注入的是 `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`。**

核查当日的配置为：

```text
OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://otel-collector:4318/v1/traces
AGENTHACK_TELEMETRY_REQUIRED=true
AGENTHACK_FLUSH_ON_SOLVE=true
```

平台还注入 `TEAM_ID`、`AGENT_ID`、`OTEL_SERVICE_NAME`、`AGENT_ROLE` 等关联信息。上述 Collector 地址是评测网络内服务地址，不应在公网本地环境中直接假定可访问。

当前注入路径不依赖镜像预先声明 `OTEL_EXPORTER_OTLP_ENDPOINT`；SDK 应能够读取 traces 专用变量。仅有 endpoint 不代表会自动出现业务 Span，Agent 仍需正确初始化并调用 SDK 的实际埋点路径。

### 2. 未配置或上传失败是否影响成绩？

需要区分三种情况：

| 情况                                     | 当前实际影响                                                                              |
| -------------------------------------- | ----------------------------------------------------------------------------------- |
| SDK 要求遥测，但初始化时没有可用 provider/endpoint   | SDK 可能抛异常，进而导致进程、健康检查或业务接口失败；不是自动扣固定分                                               |
| Agent 正常完成，但 Jaeger 没查到匹配 Trace或遥测导出失败 | 当前 `runtime_evidence_semantic_trace_required=false`，单凭缺少语义 Trace 不强制判整次失败；平台会如实记录缺失 |
| 必需的运行证据、抓包、Gateway 审计或归档完整性失败          | 当前抓包必需开关开启，相关完整性要求仍然生效，可能导致不发布有效成绩；不能把这类失败和可选 Trace 缺失混为一谈                          |

因此，“任何遥测上传失败都必然不计成绩”不符合当前配置；“遥测配置完全可以不管”同样不正确。建议保留 SDK 埋点、使用平台注入值，并在返回前按 SDK 能力执行有界 flush，不要让无限等待遥测阻塞答题。

如果缺失的是平台应注入的参数或平台采集服务不可用，应联系组委会按平台环境问题核查，不要求选手伪造 Trace。后续若将语义 Trace 改为强制条件，应另行公布，不能把未来要求倒用于历史评测。

## 四、参赛者最小自检清单

- HTTP 服务监听 `0.0.0.0:8080`，实现 `GET /health` 与 `POST /solve`。
- `/solve` 直接接收八字段题目，成功时返回 HTTP 200 与该类直接 JSON。
- 不依赖通用 SDK `TaskRequest/TaskResponse` 自动兼容赛题一，不把结果转成 `output.answer` 字符串。
- 使用 `RESEARCH_WORKSPACE_TEAM` 和 `/output` 保存本题结果，响应与磁盘文件一致；不要直接套用镜像默认 `DATA_PATH=/data` 推导输出目录。
- 模型配置、会话标识、实验授权和遥测端点均从运行时环境读取，不硬编码秘密信息。
- 单题内部截止与平台 180 秒保持一致，覆盖论文处理、模型请求及结果落盘。
- 不把“协议有效”“有 Trace”或“LLM 调用成功”当成内容满分或整次评测成功。
